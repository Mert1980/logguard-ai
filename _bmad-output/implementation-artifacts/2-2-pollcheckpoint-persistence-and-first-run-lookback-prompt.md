# Story 2.2: PollCheckpoint Persistence and First-Run Lookback Prompt

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a developer,
I want LogGuard to remember where it left off between runs and ask me how far back to look on first startup,
so that I never lose errors on restart and I can control how much backlog to process when starting fresh.

## Acceptance Criteria

1. The Flyway migration `V1__create_poll_checkpoint.sql` exists in `src/main/resources/db/migration/` and creates the `poll_checkpoint` table; Flyway now reports **1 migration applied** on a fresh DB.
2. **First run** (empty `poll_checkpoint` table): the terminal displays `"First run detected. Process last [N] hours of history? (default: 24h)"` and LogGuard **waits for developer input** before proceeding.
3. Entering a number (e.g. `6`) creates a `PollCheckpoint` with `last_successful_poll_at = now − 6 hours`.
4. Pressing Enter with no input creates a `PollCheckpoint` with `last_successful_poll_at = now − 24 hours` (the default).
5. Entering `0` creates a `PollCheckpoint` with `last_successful_poll_at = now`.
6. **Subsequent runs** (a `PollCheckpoint` already exists): no prompt is shown and the existing checkpoint is used as-is.
7. The `poll_checkpoint` table uses explicit `@Table(name = "poll_checkpoint")` and `@Column(name = "...")` on all fields — no implicit Hibernate naming (AR-7).
8. The domain `PollCheckpoint` record in `domain/model/` has **zero JPA annotations** (AR-8/AR-13).
9. `PollCheckpointRepositoryAdapter` in `infrastructure/persistence/` implements the `PollCheckpointRepository` port (`domain/port/out/`).
10. `FirstRunInitializer` in `infrastructure/config/` implements `ApplicationRunner` and prompts the developer (via Spring Shell's `Terminal` — see Dev Notes "Spring Shell on Boot 4.1" — falling back to plain stdin if Spring Shell can't be used on Boot 4.1.0).

## Dev Notes

### ⚠️ Spring Shell on Boot 4.1 — the central decision (READ FIRST)
The AC (and architecture AR-15) call for the first-run prompt to use **Spring Shell's `Terminal`**. Research this session established:
- **Spring Shell 4.0.3 is a Spring Boot 4 release** (released 2026-06-11, built on Spring Framework 7) — it is NOT a Boot 3 library.
- **BUT** the official compatibility matrix pins Spring Shell **4.0.x → Spring Boot 4.0.x**, and `spring-shell-starter:4.0.3` bundles `spring-boot-starter:4.0.7`. **Boot 4.1 is not listed as supported.** That is exactly why Initializr refused the dependency for Boot 4.1.0 in Story 2.1.
- We are on Boot **4.1.0**. Adding `spring-shell-starter:4.0.3` manually will let our `spring-boot-starter-parent:4.1.0` override the transitive `spring-boot-*` to 4.1.0; since both ride Spring Framework 7, it will **probably** work — but it is **unsupported/untested** by the Spring team.

**Approach (decided with METIS):** use Spring Shell 4.0.3 as the **primary** path (honors the AC), added manually, with `spring.shell.interactive.enabled=false`. Task 5 abstracts the actual line-read so that if Spring Shell does not wire cleanly on Boot 4.1.0, the dev swaps to the **plain-stdin fallback** (`System.console()` / `BufferedReader(System.in)`) with no structural change. FR-2 is a single one-time numeric prompt, so plain stdin fully satisfies AC #2–#6; the only thing lost in the fallback is the literal "Spring Shell Terminal" wording of AC #10 — record that as a documented deviation if it happens. **Do not burn time fighting an unsupported combo** — fall back and move on.

[Source: https://github.com/spring-projects/spring-shell/wiki/Spring-Boot-compatibility (matrix: 4.0.x↔4.0.x); spring-shell-starter:4.0.3 POM → spring-boot-starter:4.0.7.]

### ⚠️ validate + Instant + TIMESTAMP WITH TIME ZONE landmine
The app runs `spring.jpa.hibernate.ddl-auto: validate` (Story 2.1, AR-6). After Flyway creates `poll_checkpoint`, Hibernate **validates** the `PollCheckpointEntity` mapping against the actual table. Type mismatches fail startup. Guidance:
- Map `Instant` fields to `TIMESTAMP WITH TIME ZONE` columns. Hibernate 7 maps `Instant` to a UTC timestamp type that aligns with H2's `TIMESTAMP WITH TIME ZONE` — this is the expected pairing.
- If `validate` throws a type/precision mismatch at startup, align the two sides: either keep `Instant` + `TIMESTAMP WITH TIME ZONE`, or switch the column to plain `TIMESTAMP` — but do NOT silence it by switching `ddl-auto` away from `validate`.
- This is the **#1 likely failure** of this story. Verify the app starts (Task 7) and watch for a Hibernate `SchemaManagementException`.

### Schema is forward-complete (degradation columns now)
`poll_checkpoint` carries the degradation state (`degradation_started_at`, `consecutive_poll_failures`) used by Story 2.6 (FR-33–FR-36). The architecture lists **only** `V1__create_poll_checkpoint.sql` for this table (no later ALTER migration), so create all columns now. They are persisted but unused until 2.6; the domain record and entity include them so 2.6 needs no schema/mapping change. [Source: architecture.md Data Architecture lines 196–203; PollCheckpoint = "cursor + degradation state" line 446.]

### Single-row table semantics
`poll_checkpoint` holds **exactly one row, ever** (architecture line 200). The adapter's `save()` must UPDATE that row, not append a second one: on save, load the existing row's `id` (if any) and reuse it so JPA issues an update. `load()` returns `findAll().stream().findFirst()`. Keep this logic in the adapter; the domain record stays id-less.

### Ordering: prompt must precede the first poll (note for Story 2.5)
FR-2/FR-3 require the first-run prompt to complete **before** the scheduler fires its first poll. There is **no scheduler yet** (added in Story 2.5), so in this story `FirstRunInitializer` (an `ApplicationRunner`) simply runs at startup with nothing racing it. Story 2.5 must ensure the scheduler's first run (`@Scheduled(initialDelay=0)`) does not race the prompt — typically by the prompt being a blocking `ApplicationRunner` that completes before scheduling begins. Flag this in 2.5; do not solve it here. [Source: architecture.md line 169, 226–229; FR-2/FR-3.]
